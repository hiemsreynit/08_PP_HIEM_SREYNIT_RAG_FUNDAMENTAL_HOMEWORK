# Naive RAG Fundamental Homework

A simple, hands-on **Retrieval-Augmented Generation (RAG)** application built with Python, Ollama, and ChromaDB.

The project demonstrates the complete RAG workflow from document ingestion to grounded answer generation.

## What is RAG?

**RAG (Retrieval-Augmented Generation)** combines document retrieval with an LLM.

Instead of relying only on the model's pretrained knowledge, the system first retrieves relevant information from a collection of documents and provides that information as context to the LLM.

The pipeline is:

```text
Documents
    ↓
Ingestion
    ↓
Chunking
    ↓
Embeddings
    ↓
ChromaDB
    ↓
Retrieval
    ↓
Generation
    ↓
Answer
```

The LLM does not directly search the documents. The RAG system retrieves the relevant chunks and places them into the prompt.

## Configuration

The main configuration is stored in:

```text
app/config.py
```

| Setting | Value | Description |
|---|---:|---|
| `EMBED_MODEL` | `nomic-embed-text` | Embedding model |
| `GEN_MODEL` | `qwen2.5:0.5b-instruct` | Generation model |
| `DATA_DIR` | `data` | Source document directory |
| `CHROMA_DB_DIR` | `chroma_db` | Persistent ChromaDB directory |
| `COLLECTION_NAME` | `documents` | ChromaDB collection |
| `CHUNK_SIZE` | `800` | Characters per chunk |
| `CHUNK_OVERLAP` | `120` | Characters shared between chunks |
| `TOP_K` | `5` | Number of chunks retrieved |
| `SYSTEM_PROMPT` | See `config.py` | Grounding instructions |

# Running the RAG Pipeline

Each module represents an individual stage of the RAG system and can be tested independently.

## Stage 1 — Document Ingestion

```powershell
python -m app.ingestion
```

The ingestion stage:

- Finds supported documents in `data/`
- Reads their content
- Creates document metadata
- Prepares documents for chunking

---

## Stage 2 — Chunking

```powershell
python -m app.chunking
```

Documents are divided into smaller overlapping chunks.

Current settings:

```text
Chunk size    = 800 characters
Chunk overlap = 120 characters
```

The overlap helps preserve context between neighboring chunks.

---

## Stage 3 — Embeddings

```powershell
python -m app.embeddings
```

The `nomic-embed-text` model converts text into numerical vectors.

For example:

```text
"How do I schedule a conference call?"
                    ↓
             Embedding Model
                    ↓
          [0.01, -0.04, 0.12, ...]
```

These vectors represent the semantic meaning of the text.

---

## Stage 4 — Vector Store

```powershell
python -m app.vector_store
```

ChromaDB stores the document chunks and their embeddings.

The persistent vector database is stored in:

```text
chroma_db/
```

The vector store handles:

- Collection creation
- Adding document chunks
- Storing embeddings
- Similarity search
- Counting stored chunks
- Resetting the collection when required

---

## Stage 5 — Retrieval

```powershell
python -m app.retriever
```

When a question is asked, it is converted into an embedding and compared with the stored document embeddings.

The system retrieves the most relevant chunks using:

```python
TOP_K = 5
```

This means the retriever returns up to five relevant chunks for the generation stage.

---

## Stage 6 — Generation

```powershell
python -m app.generator
```

The generator combines:

```text
Retrieved Context
       +
User Question
       ↓
System Prompt
       ↓
Qwen 2.5 0.5B
       ↓
Generated Answer
```

The system prompt instructs the model to stay grounded in the provided document context.

---

## Stage 7 — Complete Pipeline

```powershell
python -m app.pipeline
```

The pipeline connects the individual RAG components:

```text
Question
   ↓
Retrieval
   ↓
Relevant Chunks
   ↓
Context Construction
   ↓
```

# Example

A question related to the provided documents:

```text
How do I schedule a conference call on Cisco Webex?
```

The RAG system processes the question as follows:

```text
Question
   ↓
Query Embedding
   ↓
ChromaDB Similarity Search
   ↓
Top 5 Relevant Chunks
   ↓
Context + Question
   ↓
Qwen 2.5 0.5B
   ↓
Grounded Answer
```

For a question that is not covered by the documents, the system is instructed to avoid using outside knowledge and follow the fallback behavior defined in `SYSTEM_PROMPT`.

# Core RAG Concepts

## 1. Chunking

Large documents are split into smaller pieces.

```text
Large Document
      ↓
Small Chunks
```

Smaller chunks make it easier to retrieve the specific information needed for a question.

## 2. Embeddings

An embedding model converts text into a vector that represents its semantic meaning.

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

## 3. Vector Database

ChromaDB stores the document chunks together with their embeddings.

```text
Document Chunk
      ↓
Embedding
      ↓
ChromaDB
```

## 4. Retrieval

The question is converted into a vector and compared with stored vectors.

```text
Question Vector
      ↓
Similarity Search
      ↓
Top-K Relevant Chunks
```

## 5. Generation

The retrieved context is passed to the LLM together with the original question.

```text
Retrieved Context + Question
              ↓
             LLM
              ↓
            Answer
```

# Troubleshooting

### Ollama is not running

Check:

```powershell
ollama list
```

Make sure the Ollama service is available at:

```text
http://localhost:11434
```

### A model is missing

Pull the required model:

```powershell
ollama pull nomic-embed-text
```

or:

```powershell
ollama pull qwen2.5:0.5b-instruct
```

### Documents are not found

Make sure your documents are inside:

```text
data/
```

and verify:

```python
DATA_DIR = "data"
```

in `app/config.py`.

### Retrieval quality is poor

Inspect the retrieved chunks before changing the LLM.

Important parameters include:

- `CHUNK_SIZE`
- `CHUNK_OVERLAP`
- `TOP_K`
- Embedding model
- Similarity scores
- Prompt construction

In a RAG system, poor answers can originate from retrieving the wrong context rather than from the LLM itself.

## Project Summary

This project implements a fundamental **Naive RAG pipeline** using local models and a local vector database.

The system follows a clear separation of responsibilities:

```text
Ingestion     → Load documents
Chunking      → Split documents
Embeddings    → Convert text to vectors
Vector Store  → Store and search vectors
Retriever     → Find relevant context
Generator     → Generate grounded answers
Pipeline      → Connect all components
Main          → Interactive application
```

The modular structure makes each stage easy to understand, test, and modify for future RAG experiments.
